# Native runtime qualification

November 9, 2026. RUNNER01 acceptance evidence covers direct native loading and
capability checks. It does not add Safetensors Start to the current chat UI.

## Safetensors CPU candidate

The earlier unpublished `safetensors.mjs` candidate is a bounded metadata parser.
It checks tensor descriptors, offsets and file identity; it contains no inference
engine. It was reviewed without copying it into the current runtime or treating
metadata discovery as successful model loading. The staged MTP candidate was
similarly reviewed against actual managed-runtime flags and observation logs.

The qualified inference candidate is the official **Mistral.rs v0.9.5 Windows
x64 CPU** executable, from source commit
`465191d0b0a7e2432d327b0de06204ab3f94d3a2`. The 34,199,612-byte release archive
has SHA-256 `64d567c299a5c97ef265aa0362649aafb968af47706810df640f74fe8ea4702a`.
The extracted 99,808,256-byte executable has SHA-256
`cdef3b664222ff469657e1e9ad8ea5846add4fe3991fd9fb2fcfb645a92b240c`.
[Candidate manifest](../build/safetensors-runtime-candidate.json) pins the source,
archive, executable, native-core revision and normalized upstream Cargo.lock.
No candidate binary is included in the a2.5 bundle.

The upstream Windows release workflow builds `mistralrs-cli` with
`cargo build --release --locked --offline`; its native Candle core is pinned to
`66a8cf184a5a519671454066b1b9efd446ec9f5c`. Safetensors is 0.8.0 and the workspace
tokenizer dependency is 0.21.4; the source lock contains other transitive versions.
The project is MIT licensed. The original notice is retained in
[MISTRALRS-LICENSE.txt](../build/licenses/MISTRALRS-LICENSE.txt).

PE import inspection found Windows OS/UCRT imports plus `VCRUNTIME140.dll` and
`VCRUNTIME140_1.dll`. The release ZIP contains only the executable. Both matching
Microsoft redistributable DLLs were placed alongside it and pinned in the
candidate manifest. Their distribution remains subject to the existing
[Microsoft redistributable notice](../build/licenses/MICROSOFT-VS18-REDIST.txt).
A full transitive static-dependency notice inventory and a clean-machine test
remain packaging gates before this candidate is distributed.

### Real-model acceptance

The Faber hub downloaded all seven files of
`hf-internal-testing/tiny-random-LlamaForCausalLM` at
`9fb191250dd56d0ba7ec9785a025ed29c03d5998`: 6,477,074 bytes total, including
4,131,280 bytes of original Safetensors weights. Length and available SHA-256
checks ran through the ordinary pinned-package download path. No conversion,
Python runtime, repository code or paid provider was used.

The official native executable loaded those original files on CPU with
`HF_HUB_OFFLINE=1`, an isolated cache, no token source and an explicit
`127.0.0.1` listener. `/v1/completions` generated eight tokens and the streaming
request completed with `[DONE]`. An MTP request failed with the explicit
requirement for PagedAttention in that native pipeline. This is a CPU/backend
capability rejection before MTP-head qualification; it does not establish that
this native runtime could use the managed GGUF runner's MTP head. This tiny random checkpoint
establishes loader/API operation, not useful output quality or architecture-wide
compatibility.

Reproduce after extracting and verifying the candidate manifest in an isolated
runtime folder outside the repository and synchronized storage:

```powershell
$env:FABER_SAFETENSORS_EXECUTABLE = '<absolute verified runtime folder>\mistralrs.exe'
$env:FABER_RUNTIME_QUALIFICATION_DIR = '<absolute isolated working folder>'
node test/safetensors-live-smoke.mjs
```

`--max-model-len 128` was rejected for this loader; its native default context
completed the test. Future managed context controls must expose actual loader
support and fail an unsupported selection explicitly.

### Managed integration gates

The native server's default bind address is `0.0.0.0`; a host adapter must force
loopback. No native API-key gate was verified. A managed integration must provide
the same authenticated, owned-process boundary as the current GGUF launcher,
using a narrow authenticated proxy or a dedicated native worker/IPC interface.

The official executable includes optional code execution capabilities, which are
disabled unless `--agent`, `--enable-code-execution` or `--enable-shell` is passed.
Those flags, MCP configuration, search and tool-dispatch configuration must not
be enabled by a model or model config. A smaller capability-specific build is
an alternative to redistributing the full CLI. No native listener remained
running after qualification.

## Managed llama.cpp MTP

The existing managed native runner identifies commit
`a37cc46104eb50900d5ab4a9ba02a0abdac039db`. Its actual help advertises
`--spec-type draft-mtp`, `--spec-draft-n-max`, `--spec-draft-model`, `--slots`
and trace verbosity. Source inspection at that exact commit confirms a registered
MTP implementation, native NextN model-context construction and explicit failure
when a model lacks an MTP head. A command-line flag alone is not treated as proof
that a particular model supports MTP.

The real positive checkpoint was
`unsloth/Qwen3.5-0.8B-MTP-GGUF` at
`cf8a611f6ed2c2060046219a19f12cd3d5ecd67c`, file
`Qwen3.5-0.8B-Q4_K_M.gguf` (549,698,976 bytes), SHA-256
`ac7c9d7a1b3e3695bb3bd50f8ceaa97f9c93e99ccc3d3d1a620301b6dd6d3d86`.
The native metadata reader verified `qwen35`, 335 tensor descriptors and actual
`blk.24.nextn.eh_proj`, `enorm`, `hnorm` and `shared_head_norm` tensors.

CPU baseline and MTP runs each generated 32 tokens at temperature zero, with the
same output for this sample. The MTP run reported 23 draft tokens and 23 accepted
tokens; `/slots` reported `speculative:true`, and initialization logs contained
the selected `draft-mtp` implementation and successful speculative context.
These checks establish actual drafting. Short timing samples are not a sustained
performance claim.

The pinned negative fixture was `tinyllamas/stories260K.gguf` from
`ggml-org/models-moved` at `499bc8821c6b12b4e53c5bffcb21ec206f212d81`.
With MTP requested it exited with code 1 and reported that it lacked MTP layers;
it never became ready through an implicit fallback.

```powershell
$env:FABER_LLAMA_EXECUTABLE = '<absolute existing managed runtime>\llama-server.exe'
$env:FABER_RUNTIME_QUALIFICATION_DIR = '<absolute isolated working folder>'
node test/mtp-live-smoke.mjs
```

All servers used explicit loopback binding, random ports and per-process random
API secrets. Processes were stopped after the tests. Separate MTP head pairing,
other architectures, GPU execution, user-facing controls and performance across
prompts/context sizes remain separate acceptance work.
