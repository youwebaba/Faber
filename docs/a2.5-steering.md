# a2.5 runtime and steering verification

## Implemented behavior

`chat.send` retains the durable follow-up queue. `chat.steer` accepts
`{chatId,runId,text,images?,correctionId?}` for the intended active run. A stale
run is rejected; the same correction ID reconciles a previous receipt, including
after completion. Changed input or a different run cannot reuse that ID.
Paired workspaces advertise `steering:true` and use the same host operation.

For HTTP generation, steering interrupts only the model attempt, discards
undispatched arguments and resumes the same run with the correction. An executing
tool finishes under its existing authority; its result remains recorded. A tool
still awaiting approval and later superseded actions do not execute. Stop aborts
the affected run tree before saving or broadcasting historical state.

Official GPT-6 API-key Responses connections use WebSocket steering. The trace
distinguishes queued input, server acceptance and application at the successor
response. Accepted input is never resent automatically. A lost acknowledgement
or continuation produces an unknown outcome. Required tool-input continuations
return explicit superseded results for actions that were never dispatched.
ChatGPT subscription connections use the HTTP interruption path; subscription
WebSocket steering has not been established. These semantics follow the
[OpenAI steering guide](https://developers.openai.com/api/docs/guides/steering)
and [WebSocket guide](https://developers.openai.com/api/docs/guides/websocket-mode).

Live output counters include streamed tool arguments. Counts are labeled
reported, estimated or pending and advance on provider events. Tool waiting has
no generated-token timer. Prompt usage sums each call once, including retries,
compaction and attributable descendants. Missing counts remain identifiable;
cached input and reasoning remain subsets. When several prompts share one call,
earlier rows identify the prompt owning that call instead of duplicating its
counts. Rejected or aborted streams release their transport and invoke iterator
cleanup without waiting indefinitely for `return()`.

## Observed checks

The focused deterministic suite passed **191 tests with zero failures**. It
covers Stop ordering, an abort-ignoring iterator, real loopback HTTP cleanup,
approval and running-tool races, completion races, reconnect deduplication,
usage attribution, and native protocol fixtures. WebSocket fixtures include
late acceptance, duplicate controls, required-input continuations, empty
terminal snapshots and unknown disconnect outcomes.

Actual local inference used Qwen3.5-0.8B Q4_K_M with the qualified Windows
llama.cpp CPU runner, two threads and an 8192-token context. The repeatable
acceptance advertised one write tool with greedy sampling. Both the local case
and a real pinned-TLS connection through a local WebSocket relay showed:

- An estimated 20 generated argument tokens before any write dispatched.
- The original model attempt interrupted and the same run resumed.
- No obsolete file and exactly one corrected HTML file.
- Two completed calls totaling 1332 reported input tokens, 59 output tokens and
  1167 cached-input tokens. The interrupted call's usage remained unknown.
- One applied correction after deliberately dropping its receipt, recreating
  the controller and reconciling the same correction ID with a fresh request.
- A stopped owned runner and zero remaining relay rooms, sockets or sessions.

The fixture's input estimate includes the runtime registry before its adapter
narrows advertised tools; its provider-reported counts are the actual counts.
The reproducible check is `test/a25-runtime-live.mjs`; the sanitized local report
is `release/verification/a25-runtime-live/report.json`.

One full-registry local check also passed. A full-registry remote trial exposed
a model-selection failure: the 0.8B model chose an unrelated project operation.
Project approval blocked it, and the run timed out without creating a project
or writing a file. This limits the evidence for that model's general tool use.

Both OpenAI connection types passed a live steering check in a disposable chat.
Each response had a limit of 256 output tokens and the model received no tools.

- **OpenAI API key.** Native WebSocket steering applied in 4.694 seconds.
  The original response was interrupted and its automatic successor completed
  with the corrected answer.
- **ChatGPT subscription.** HTTP interruption and replacement applied
  the correction in 5.407 seconds, under the same run. This verifies the fallback
  path; subscription-native WebSocket steering remains unverified.

The one-time diagnostic and its consumed-authorization ledger remain in ignored
private verification storage. No additional paid checks were made. The broader
native error, reconnect and tool-boundary matrix remains covered by protocol
fixtures. Physical two-PC/WAN acceptance remains open; the real TLS relay checks
used isolated services on one PC.
