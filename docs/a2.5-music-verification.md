# a2.5 local Music3 verification

Verified on Windows x64 with the bundled **CPU** runner. No paid provider or
cloud model calls were made. These results establish one short real generation
and its chat delivery/playback; they do not establish musical quality or normal
song-length performance.

## Real generation and media delivery

[The opt-in live smoke](../test/music-live-smoke.mjs) invoked `music_generate`
through Faber's shared tool registry with the chat's files grant. The request
used a self-authored piano instrumental caption, section-tagged lyrics, a
four-second target, two synthesis steps and seed 42.

- Real CPU generation plus durable media delivery: **48.808 seconds**.
- Output: **704,556 bytes**, stereo **44,100 Hz PCM16 WAV**, **3.993832 seconds**.
- Normalized waveform RMS: **0.094713**; peak: **0.999969**. The output was
  measured as non-silent; this is not a musical-quality judgment.
- Output SHA-256:
  `046f4356a7710376a1eebf90d4876d4139795c47679bc776982a361b16e71488`.
- Chat/API provider calls: **0**.

The registry persisted an ordinary chat-owned media reference. The smoke read
the audio back through `chat.media` in bounded chunks and validated its format
and waveform. An earlier direct adapter run independently generated a real
four-second WAV in 46.235 seconds; it is separate evidence, not the output above.

## Actual generated-audio playback

[The Electron media smoke](../test/desktop-media-smoke.mjs), supplied the actual
generated WAV through `FABER_MUSIC_SMOKE_AUDIO`, passed **11 checks** and used
**17 media chunk requests**. Its recorded audio SHA-256 matched the generation
fingerprint above.

- Local and paired remote audio reached `canplay`, advanced during playback,
  sought successfully and retained the player across state updates.
- Local and remote Save As transfers retained the exact generated bytes.
- Remote offlining released player sources; host revocation denied later reads.
- The production preload, media protocol, CSP and encrypted TLS/WebSocket relay
  were exercised. Remote media chunks retained the existing 256 KiB ceiling.

The relay ran on **loopback**, not two physical PCs or a WAN. Native Save As and
clipboard writers were intercepted; the user's clipboard was untouched. Video
and image portions of the shared smoke remained synthetic fixtures. Playback
was programmatically verified with muted players, not subjectively auditioned.

## Deterministic checks and limits

`node --test test/music.test.mjs` passed **5/5** checks covering five-component
request routing, actual architecture validation, bounded durable audio,
cross-chat media denial, argument validation, cancellation of an owned process,
close/concurrency cleanup and tampered/unreviewed runtime rejection.

Runner manifest verification, tool-schema validation, syntax checks and
`git diff --check` also passed. Complete application-suite and installer results
are recorded by the integrated release verification separately.

No GPU music backend, long/full-quality song, physical two-PC/WAN session,
microphone/speaker audition or independent music-quality assessment was tested.
The chat's configured overall run deadline applies to CPU generation; longer
jobs may require a larger limit. Hard host crashes retain the existing owned
process cleanup limitation described in `killOwnedProcess`; this release does
not add Windows Job Objects.
