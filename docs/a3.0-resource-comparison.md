# Matched transcript and upgrade retention measurements

The 2026-11-09 comparison ran a2.4 source read-only and the integrated a3.0
renderer in the same Electron 45.2.1 runtime. It used new temporary profiles,
synthetic remote responses and controlled source fixtures. No owner profile,
daily trial, scheduled task, installed application or live desktop was changed.

Run the same standalone probes with:

```powershell
node test/qa-resource-compare.mjs '<absolute a2.4 source root>' '<absolute current source root>'
```

The comparison writes its JSON reports to a new temporary directory. Each
renderer report records the fixture hash and hashes of the actual selected
remote-workspace, transcript and activity modules. The upgrade report records
the selected upgrade-manager hash. Source labels alone are not the provenance.

## Actual Chromium DOM retention

The unchanged renderer modules ran in sandboxed offscreen BrowserWindows with
real DOM, synthetic typed RPC responses and no Node or app bridge in the page.
Both versions started with 20 saved messages per chat. The fixture completed
80 unique streamed runs in one chat, then changed through 30 other chats.
Each finished run added one legitimate saved message. Those connected messages
are retained history, not a leak.

WeakRefs tracked the created element wrappers without keeping them alive.
A weak observer on native `Map.set` separately counted actual reachable DOM
cache entries; source modules and their private maps were not rewritten. Before
every sample, the fixture flushed layout and two offscreen animation frames,
then forced collection twice. This matters: an initial hidden-window probe
without the frame flush retained pending Blink layout trees after chat changes.
Those preliminary detached-message counts are excluded from the final results.

| Phase | a2.4 connected messages | a2.4 detached streams | a3.0 connected messages | a3.0 detached streams |
| --- | ---: | ---: | ---: | ---: |
| Initial chat | 20 | 0 | 20 | 0 |
| 40 finished runs | 60 | 40 | 60 | 0 |
| 80 finished runs | 100 | 80 | 100 | 0 |
| After 30 chat changes | 20 | 0 | 20 | 0 |
| After workspace dispose, API retained | 20 | 0 | 0 | 0 |
| After API release | 20 | 0 | 0 | 0 |

After 80 runs, the observed message-cache roots were 180 in a2.4: 100 legitimate
saved messages and 80 retired stream articles. a3.0 had 100 saved messages and
zero retired stream articles. WeakRef/GC counts agreed with direct cache-entry
observations. After disposal a3.0 retained no message or stream wrappers, even
when the fixture still held the public workspace API object. a2.4 retained the
20 messages in its hidden mounted workspace.

The first integrated measurement also found 80 detached activity-card roots in
both versions during the 80-run same-chat phase, with matching reachable Map
entries. The owning activity component now prunes card, tool and prompt-usage
indexes after normal local and remote transcript reconciliation. It removes
only nodes outside that transcript; visible nodes keep their identity, expanded
state and keyboard focus. Existing scope-switch/reset behavior is preserved.

| Activity-card cache phase | a2.4 | a3.0 before owner fix | a3.0 after owner fix |
| --- | ---: | ---: | ---: |
| 40 finished runs, same chat | 40 detached | 40 detached | 0 |
| 80 finished runs, same chat | 80 detached | 80 detached | 0 |
| After chat changes/disposal | 0 | 0 | 0 |

The identical matched fixture was rerun after the owner fix. The final a3.0
measurement had zero detached activity, message and stream roots after 80
finished runs. Its 100 legitimate connected saved-message roots remained.
Both the real remote workspace and an 80-cycle real-DOM local activity owner
check preserved visible identity, expanded disclosure and focused summaries
across live updates. The local check also retained the same expanded tool node.
A targeted unit regression verifies that retired card/tool/usage entries and
scope-reset indexes are recreated rather than retained. The normal full app
Electron renderer/bridge smoke passed after the shared call-site changes.

## Real file-backed upgrade staging and rollback

Each selected release's actual upgrade manager operated on an identical
2,097,152-byte source payload: eight files plus a small value module and test.
The fixture staged, ran the real Node tests and applied eight changes. It then
left one unused stage, reconstructed the manager, invoked startup expiration
where that release implements it, and rolled back the eighth applied change.
No test runner or filesystem operation was mocked. Rollback restored the
expected prior module bytes in both versions.

| Phase | a2.4 logical bytes | a2.4 stage directories | a3.0 logical bytes | a3.0 stage directories |
| --- | ---: | ---: | ---: | ---: |
| One applied change | 4,198,375 | 1 | 2,101,189 | 0 |
| Four applied changes | 16,787,146 | 4 | 8,399,623 | 0 |
| Eight applied changes | 33,572,174 | 8 | 16,797,535 | 0 |
| Plus one unused stage | 35,669,448 | 9 | 18,894,809 | 1 |
| After manager restart/startup cleanup | 35,669,448 | 9 | 16,797,535 | 0 |
| After verified real rollback | 37,768,437 | 9 | 18,896,524 | 0 |

a2.4 has no startup stage-expiration method. a3.0 removed the unused stage;
applied stage copies had already been removed. The eight-apply fixture retained
about 50% fewer logical bytes in a3.0, while preserving all eight rollback
backups. The verified rollback added a ninth intentional recovery backup in
each version. Cleanup is not permission to remove those durable records.

Upgrade-manager SHA-256 values were
`37675c568dce0d336719c34f9db6223919d65d35e317c144db54b000fefcb5a4`
for a2.4 and
`47eab343609704b5291af4de66f134742f97bf58c50c9ee28b23d95a0c6b1bb1`
for the measured a3.0 source.

## Limits

These are measured DOM-wrapper/cache counts and logical file bytes, not total
JavaScript heap, native DOM allocation, disk allocation, GPU memory or installer
size. The renderer fixture covers the real remote workspace component, not the
entire local app, user-driven desktop or physical network. The upgrade fixture
does not compile native payloads or exercise NSIS. It preserves backups and
uses real test/verify/apply/restore behavior on its own small source tree.
Other QA04 transfer/cookie/state/Stop measurements retain their own matched
fixtures. These results do not complete sustained seven-day resource acceptance.
