# a2.6 worker and routine verification

The worker/routine checks use disposable profiles and controlled inputs. No
owner login entry, saved credential or private project was changed. The Windows
acceptance harness uses a deterministic provider with real Electron processes,
real files and real worker/renderer termination. It makes zero provider-network
calls; this does not claim a live-model daily-report trial.

## Actual Windows lifecycle

`node test/desktop-worker-live.mjs` exercised:

- The normal Routines form saved a revision, previewed a proposed write without
  executing it, then explicitly enabled and manually queued work.
- Closing **every window** retained the same worker/run. Exactly one report
  committed while the UI was absent.
- A second Faber launch reused the existing owner and opened a fresh renderer.
- An actual renderer crash left its job running; reopening showed one completed
  result, with no duplicate output.
- A pending approval survived UI closure. The write ran once only after
  explicit approval in the reopened UI.
- The hidden sign-in launch mode created no window. A normal second launch
  opened a genuinely visible UI connected to that same worker.
- Explicit Quit completed shutdown. The next process acquired the profile
  again without leaving a live writer behind.

The lifecycle fixture completed one preview and three manual jobs. Each of its
three distinct report paths was written exactly once. The sign-in API argument
tests use a fake registration adapter; no real login registration was enabled.

## Actual main-worker crashes

The harness terminates the Electron main process at controlled boundaries,
then relaunches the same isolated profile. Kernel ownership was reclaimed and
Safe Mode paused automatic admission in every case.

| Interruption | Recovery result | Automatic repeats |
| --- | --- | --- |
| Immediately before a write | Needs attention; destination did not verify the intent | 0 |
| After atomic file commit, before recording its result | One output reconciled by exact digest; continuation needs review | 0 |
| After a controlled external-effect stand-in (local append), before its result | Needs attention with unknown effects; append remained a single line | 0 |

All recovered jobs retained their stable IDs and one recorded attempt. The
external-effect stand-in is a local append, not a real mail send or paid API
action. It proves the unknown-effect/no-replay path without performing an
irreversible external action.

## Deterministic and renderer checks

[Routine tests](../test/core-routines.test.mjs) cover revision immutability,
future-only edits, scope/path escape, preview, revocation, approval denial,
connection/credential changes, interaction waits, receipts and destination
reconciliation, stable bounded read-only recovery, action-key reuse and input
receipts surviving activity-chat deletion.

A targeted race test steers while the pre-dispatch intent is being persisted.
The superseded file write never executes. Existing a2.5 Stop/steering tests pass
alongside these checks. Shutdown also tracks terminal-but-settling runs, so
`close()` cannot return before their final job/run state is saved.

[Background tests](../test/desktop-background.test.mjs) cover separate opt-ins,
profile-bound login arguments, smoke-mode refusal to change login registration,
second-writer rejection and ownership reclamation.

The ordinary Electron smoke passed with the a2.6 label, sandboxed bridge,
Routines navigation, 90 registered tools, connection controls, attachments,
reasoning controls and the existing extension action. Integrated suite counts
are recorded in the release's overall verification record after all a2.6 work
is combined.

At the final worker checkpoint, the complete source suite passed **664 tests,
zero failures and one optional native-input skip (665 total)**. The focused
worker/routine plus inherited Stop/steering run passed **37/37**.

## Limits

Actual Windows sign-out/sign-in registration was not enabled on the owner's
account. No real screen lock, desktop pointer interaction, boot-before-sign-in
service, sleep/wake scheduler, physical two-PC trial or seven-day trial was run.
Those outcomes are not inferred from the deterministic provider or shortened
clock tests. Schedules, budgets and the daily folder-report routine belong to
a2.7; eligible boot-time work belongs to a2.9.

A future seven-day trial starts only after the actual scheduled folder report
has passed its real local-model and recovery checks. Record its real UTC start,
expected occurrences, interventions and observed results; simulated elapsed
time cannot complete that gate.
